# Requirements Document

# LangGraph Agent Loop

## Introduction

This specification defines the core stateful text-to-SQL agent loop built on LangGraph. The agent orchestrates 8 specialized nodes that break down natural-language questions into executable SQL, validate and execute queries safely, recover from errors via structured retries, and track conversation state through bounded iterations and retry budgets. The system enforces deterministic safety guarantees through plain Python validation and execution layers while using LLMs only for generation and interpretation tasks.

## Glossary

- **Agent**: The LangGraph state machine that orchestrates all 8 nodes and routing decisions.
- **AgentState**: TypedDict that carries conversation context, query history, and execution state across all nodes.
- **Node**: A callable that processes AgentState and returns an updated state dict. Some nodes call LLMs; others are deterministic.
- **LLM Node**: A node that calls a language model (planner, generate_sql, fix_sql, analyze_result).
- **Deterministic Node**: A node that contains no LLM calls and produces repeatable results (validate_sql, execute_sql, retrieve_schema, load_memory, save_memory).
- **Plan**: An ordered list of steps generated by the Planner to resolve the user's question.
- **Schema Context**: The relevant tables, columns, types, and relationships for the current question (retrieved by retrieve_schema).
- **Destructive SQL**: SQL statements that modify or drop data (INSERT, UPDATE, DELETE, DROP, CREATE, ALTER, TRUNCATE).
- **Iteration**: Each time any node completes, the state's `iterations` counter increments. When `iterations >= MAX_ITERATIONS (10)`, the agent must transition to final_answer.
- **Retry**: An attempt to fix a failed SQL query via the fix_sql node. Retries are capped at MAX_RETRIES (3).
- **Validation Result**: A dict with keys `{ok: bool, reason?: str, tables_used?: set, sql?: str}` indicating whether SQL passed safety checks.
- **Execution Result**: A dict with keys `{columns: list, rows: list, row_count: int}` returned from the target database, or an error dict on failure.
- **Status**: One of `["running", "answered", "rejected", "failed", "needs_clarification"]`, representing the agent's current state. Only final_answer nodes may set non-"running" values.
- **Conversation ID**: Unique identifier for a multi-turn conversation; used to load and save memory.
- **User ID**: Identifier of the user asking the question; used for memory scoping and audit logging.

## Requirements

### Requirement 1: AgentState TypedDict Definition

**User Story:** As a developer, I want a well-typed state container that carries all context through the agent loop, so that nodes can safely access and update conversation state without runtime surprises.

#### Acceptance Criteria

1. WHEN the Agent initializes, THE AgentState TypedDict SHALL contain all and only these fields:
   - `conversation_id: str`
   - `user_id: str`
   - `question: str` (the user's original question)
   - `history: list[dict]` (previous Q/SQL/result tuples)
   - `plan: list[str]` (ordered steps from the planner)
   - `needs_schema: bool` (flag set by planner)
   - `schema_context: str` (relevant tables and columns)
   - `sql: Optional[str]` (generated or fixed SQL)
   - `validation: Optional[dict]` (result of validate_sql: `{ok, reason?, tables_used?, sql?}`)
   - `result: Optional[dict]` (result of execute_sql: `{columns, rows, row_count}` or error dict)
   - `error: Optional[str]` (execution error message)
   - `retries: int` (count of fix_sql attempts)
   - `iterations: int` (count of nodes executed)
   - `status: Literal["running", "answered", "rejected", "failed", "needs_clarification"]`
   - `answer: Optional[str]` (final natural-language answer to user)

2. THE AgentState SHALL be importable from `app.agent.state` as `AgentState` with no import errors.

3. WHEN type-checking with mypy or similar, THE AgentState definition SHALL pass without errors.

4. WHERE a node accesses a field not in AgentState, THE type checker SHALL report an error.

### Requirement 2: Eight Nodes Defined and Callable

**User Story:** As a developer, I want each node to be independently callable and testable, so I can verify routing logic and node behavior in isolation.

#### Acceptance Criteria

1. THE following eight nodes SHALL be defined in `app/agent/nodes/` and importable:
   - `load_memory`: loads prior conversation turns from memory
   - `planner`: breaks the question into steps, decides schema retrieval need, flags ambiguity
   - `retrieve_schema`: returns only relevant tables, columns, types, and relationships
   - `generate_sql`: produces SQL from plan, schema, and history
   - `validate_sql`: parses and checks SQL for safety (no import of LLM)
   - `execute_sql`: runs SQL on target DB with timeout and row limits (deterministic)
   - `fix_sql`: corrects SQL given error and schema context
   - `analyze_result`: summarizes and flags anomalies (no import of LLM)
   - `save_memory`: persists turn to PostgreSQL

2. EACH node SHALL be a callable with signature `(state: dict[str, Any]) -> dict[str, Any]` and SHALL return an updated state dict with at minimum `iterations: int` incremented by 1.

3. WHEN a node is imported via `from app.agent.nodes.<name> import <name>`, THE function SHALL be callable without errors.

4. WHERE a node is deterministic (validate_sql, execute_sql, retrieve_schema, load_memory, save_memory), THE import statement SHALL NOT include any LLM library (langchain, litellm, anthropic, openai) at module level, AND IF such an import is detected, THE node SHALL fail hard (raise ImportError or be rejected during module load) and SHALL NOT be registered/callable in the graph.

5. WHERE a node is an LLM node (planner, generate_sql, fix_sql, analyze_result), THE node SHALL receive an LLM client from config and call it to produce a response.

### Requirement 3: LangGraph State Machine Compiles Without Errors

**User Story:** As a developer, I want the graph to compile and define all edges without cycles or unhandled transitions, so the agent can run end-to-end.

#### Acceptance Criteria

1. WHEN `app/agent/graph.py` is imported, THE StateGraph SHALL be created with AgentState and all 8 nodes added without errors.

2. THE graph SHALL define conditional edges that route:
   - From `planner` to `final_answer` IF status is `needs_clarification`, else to `retrieve_schema` IF `needs_schema` is True, else to `generate_sql`
   - From `validate_sql` to `execute_sql` IF validation passed, else to `fix_sql` IF `retries < MAX_RETRIES`, else to `final_answer`
   - From `execute_sql` to:
     - `final_answer` IF `iterations >= MAX_ITERATIONS`
     - `analyze_result` IF no error
     - `fix_sql` IF error and `retries < MAX_RETRIES`, else `final_answer`
   - From `fix_sql` to `validate_sql` (after incrementing retries)

3. THE graph SHALL call `set_entry_point("load_memory")` to start from load_memory.

4. THE graph SHALL call `set_finish_point("save_memory")` so all paths end at save_memory before final_answer.

5. WHEN the graph is compiled via `.compile()`, THE result SHALL be a callable RunnableGraph with no errors.

6. THE graph SHALL have exactly one path from load_memory to final_answer for every legal state trajectory.

### Requirement 4: Planner Returns Structured JSON with Validation

**User Story:** As a developer, I want the planner to return a parseable, validated structure, so downstream nodes can rely on its output schema.

#### Acceptance Criteria

1. THE Planner node SHALL call an LLM with a prompt instructing it to return JSON in this exact schema:
   ```json
   {
     "plan": ["step 1", "step 2", ...],
     "needs_schema": true/false,
     "ambiguity_flag": true/false,
     "clarifying_question": "optional question to ask user"
   }
   ```

2. WHEN the LLM returns malformed JSON, THE Planner SHALL retry up to 3 times with an error message asking the LLM to correct the JSON.

3. IF after 3 retries the JSON is still invalid, THE Planner SHALL set `status: "failed"` and `error: "Planner could not produce valid JSON after retries"`.

4. IF `ambiguity_flag` is true, THE Planner SHALL set `status: "needs_clarification"` and `answer: clarifying_question`, so that final_answer will return the clarifying question instead of attempting SQL generation.

5. WHEN valid JSON is returned, THE Planner SHALL:
   - Update `state["plan"]` with the plan list
   - Update `state["needs_schema"]` with the boolean
   - Set `state["status"] = "running"` (keep agent running)

6. THE Planner prompt file SHALL be stored at `app/prompts/planner.txt` and versioned.

### Requirement 5: Every Node Increments Iterations

**User Story:** As a developer, I want iteration count to track progress and enforce the iteration budget, so long-running agents cannot loop indefinitely.

#### Acceptance Criteria

1. EVERY node (all 8) SHALL increment `state["iterations"]` by exactly 1 before returning.

2. WHEN a node checks the iteration budget, it SHALL compare `state["iterations"] >= MAX_ITERATIONS (10)` and set `status: "failed"` with appropriate error if exceeded.

3. WHERE a node increments iterations, IT SHALL ensure the incremented value is returned in the output state dict.

### Requirement 6: Iterations Budget Enforced at MAX_ITERATIONS = 10

**User Story:** As a developer, I want the agent to halt after 10 node executions regardless of state, so runaway loops are impossible.

#### Acceptance Criteria

1. THE constant `MAX_ITERATIONS` SHALL be defined as 10 in `app/agent/graph.py`.

2. AFTER any node executes and increments iterations, IF `iterations >= 10`, THE agent SHALL route directly to `final_answer` regardless of current node or next-node logic.

3. WHEN final_answer is reached due to iteration budget, IT SHALL set `status: "failed"` if not already set, and `error: "Iteration budget exhausted (10 iterations executed)"`.

4. THE `final_answer` node SHALL always check `iterations >= MAX_ITERATIONS` before processing other state conditions.

### Requirement 7: fix_sql Receives All Required Context

**User Story:** As a developer, I want fix_sql to have complete information to suggest corrections, so it can produce better fixes.

#### Acceptance Criteria

1. WHEN `fix_sql` is called, THE state SHALL contain a fixed, explicit set of fields:
   - `question: str` (the user's original question)
   - `plan: list[str]` (the steps generated by planner)
   - `sql: str` (the SQL that failed)
   - `error: str` (the error message from execution)
   - `schema_context: str` (relevant tables and columns)

2. THE fix_sql node SHALL pass all of these to the LLM prompt along with the user's original question and plan.

3. THE LLM prompt file for fix_sql SHALL be stored at `app/prompts/fix_sql.txt` and versioned.

4. WHEN fix_sql returns SQL, IT SHALL increment `state["retries"]` by 1 and return the updated state with `sql: <new_sql>` and `iterations` incremented.

### Requirement 8: Destructive SQL Detected and Immediately Rejected

**User Story:** As a developer, I want destructive SQL rejected immediately without retry, so the agent cannot accidentally execute modifications.

#### Acceptance Criteria

1. WHEN validate_sql detects a destructive statement (INSERT, UPDATE, DELETE, DROP, CREATE, ALTER, TRUNCATE, or system catalog access), IT SHALL return:
   ```python
   {"ok": False, "reason": "Destructive or forbidden operation detected", "destructive": True}
   ```

2. WHEN validate_sql returns `{"ok": False, "destructive": True}`, THE agent router SHALL NOT route to fix_sql; instead, it SHALL route directly to `final_answer`.

3. AT final_answer, IF the validation indicated destructive SQL, THE agent SHALL set:
   - `status: "rejected"`
   - `answer: "Your question would require a write operation, which is not allowed. Only SELECT queries are supported."`

4. THE validate_sql implementation SHALL use sqlglot AST parsing (not regex) to detect destructive operations.

### Requirement 9: Fixed SQL Validated After fix_sql Node

**User Story:** As a developer, I want to be certain that fixed SQL also passes validation, so the agent doesn't execute invalid SQL.

#### Acceptance Criteria

1. WHEN fix_sql returns a corrected SQL, THE state SHALL route to validate_sql (not directly to execute_sql).

2. AT validate_sql (the second pass), THE result SHALL be validated with the same checks as the first pass.

3. IF the second validation also fails, THE agent SHALL check if `retries < MAX_RETRIES`; if yes, route to fix_sql again; if no, route to final_answer with `status: "failed"`.

### Requirement 10: Load Memory and Save Memory Are Deterministic

**User Story:** As a developer, I want memory operations to be pure Python functions, so they don't depend on LLM behavior.

#### Acceptance Criteria

1. THE load_memory node SHALL:
   - Accept a conversation_id and user_id from the state
   - Query the app DB (PostgreSQL) for the last N turns of this conversation
   - Populate `state["history"]` with the result
   - Return the updated state with `iterations` incremented
   - NOT call any LLM

2. THE save_memory node SHALL:
   - Write the completed turn to the app DB (conversation_id, user_id, question, plan, sql, result, answer, status, timestamp)
   - Increment `iterations`
   - Return the updated state
   - NOT call any LLM

3. IF database connection fails, BOTH load_memory and save_memory SHALL raise a single shared custom exception type (e.g., `MemoryConnectionError`) that wraps the underlying driver error but does not expose connection strings, API keys, or other secrets.

### Requirement 11: Planner Prompt Versioned and Documented

**User Story:** As a developer, I want to iterate on prompts without breaking existing tests, so I can improve LLM output over time.

#### Acceptance Criteria

1. THE prompt file `app/prompts/planner.txt` SHALL be stored as plain text and versioned in git.

2. THE planner prompt file `app/prompts/planner.txt` SHALL instruct the LLM to:
   - Break the user's question into logical steps (task decomposition)
   - Decide whether retrieving the database schema is necessary
   - Flag if the question is ambiguous and include a clarifying question if so
   - Return JSON in the exact schema specified in Requirement 4

3. THE prompt SHALL include 2–3 few-shot examples showing expected output for different question types.

### Requirement 12: Generate SQL Prompt Versioned and Documented

**User Story:** As a developer, I want to control SQL generation quality through versioned prompts, so I can measure improvements.

#### Acceptance Criteria

1. THE prompt file `app/prompts/generate_sql.txt` SHALL be stored as plain text and versioned in git.

2. THE prompt SHALL instruct the LLM to:
   - Use the provided schema context (tables, columns, relationships)
   - Follow the plan provided by the planner
   - Reference the conversation history for context
   - Output ONLY valid PostgreSQL syntax
   - Include comments explaining key joins or calculations

3. THE prompt SHALL include examples of correct SQL for sample questions.

### Requirement 13: Fix SQL Prompt Versioned and Documented

**User Story:** As a developer, I want the LLM to understand why SQL failed, so it can suggest meaningful fixes.

#### Acceptance Criteria

1. THE prompt file `app/prompts/fix_sql.txt` SHALL be stored as plain text and versioned in git.

2. THE fix_sql prompt file `app/prompts/fix_sql.txt` SHALL instruct the LLM to:
   - Analyze the original SQL query and the error message from execution
   - Identify the root cause of the failure
   - Produce corrected SQL that addresses the identified error
   - Output the corrected query with explanation comments

3. THE prompt SHALL include 2–3 examples of common SQL errors and their fixes.

### Requirement 14: Analyze Result Prompt Versioned and Documented

**User Story:** As a developer, I want results summarized and flagged for anomalies, so users understand the data they receive.

#### Acceptance Criteria

1. THE prompt file `app/prompts/analyze_result.txt` SHALL be stored as plain text and versioned in git.

2. THE prompt SHALL instruct the LLM to:
   - Summarize the SQL result in natural language
   - Flag if the result is empty, has excessive NULLs, or seems unusual
   - Answer the user's original question based on the result
   - Keep the answer concise (under 200 words)

3. WHEN analyze_result completes, IT SHALL set:
   - `state["answer"]` to the LLM-generated summary
   - `state["status"]` to "answered" (unless a prior error occurred)

### Requirement 15: Validate SQL Is Deterministic (No LLM)

**User Story:** As a developer, I want SQL validation to be 100% predictable and sandboxed, so invalid SQL cannot slip through.

#### Acceptance Criteria

1. THE validate_sql node SHALL NOT import or call any LLM.

2. THE validate_sql function SHALL:
   - Parse the SQL using sqlglot with PostgreSQL dialect
   - Reject if not a SELECT (or CTE containing SELECT)
   - Reject if contains INSERT, UPDATE, DELETE, DROP, CREATE, ALTER, TRUNCATE
   - Reject if references forbidden functions (pg_sleep, pg_read_file, dblink, set_config) or system catalogs
   - Reject if uses unknown tables (not in allowed_tables or CTEs)
   - Check the row limit and add/enforce a `LIMIT 1000` if missing
   - Return `{"ok": True, "sql": <normalized_sql>, "tables_used": <set>}` on success
   - Return `{"ok": False, "reason": <error_text>, "destructive": <bool>}` on failure

3. WHEN validate_sql is called, THE function SHALL return immediately without network calls or async operations.

### Requirement 16: Execute SQL Is Deterministic (No LLM)

**User Story:** As a developer, I want SQL execution to be deterministic and safe, so runaway queries cannot harm the database.

#### Acceptance Criteria

1. THE execute_sql node SHALL NOT import or call any LLM.

2. THE execute_sql function SHALL:
   - Connect to the target database using the readonly role
   - Set the transaction to READ ONLY
   - Set statement_timeout to 5 seconds (from config)
   - Execute the SQL
   - Fetch up to 1000 rows (from config)
   - Return `{"columns": [<list>], "rows": [<list>], "row_count": <int>}`

3. WHEN a query times out (timeout exceeds 5s), THE execute_sql node SHALL catch the timeout exception internally and return:
   ```python
   {"ok": False, "error": "Query timed out after 5 seconds"}
   ```
   (The exception SHALL NOT propagate; it MUST be caught before returning.)

4. WHEN a query returns more than 1000 rows, THE execute_sql SHALL truncate to 1000 and return:
   ```python
   {"ok": False, "error": "Result exceeds row limit (1000); truncated. Refine your query.", "columns": [...], "rows": [...], "row_count": 1001+}
   ```

5. WHEN query execution fails (syntax, permission, etc.), execute_sql SHALL return:
   ```python
   {"ok": False, "error": "<database error message>"}
   ```

### Requirement 17: Retrieve Schema Is Deterministic (No LLM)

**User Story:** As a developer, I want schema retrieval to be pure Python, so it's fast and predictable.

#### Acceptance Criteria

1. THE retrieve_schema node SHALL NOT import or call any LLM.

2. THE retrieve_schema function SHALL query the target database system catalogs (pg_tables, pg_columns, etc.) and return:
   ```python
   {
     "tables": {
       "table_name": {
         "columns": [{"name": "col", "type": "integer", "nullable": true}, ...],
         "primary_key": ["id"],
         "foreign_keys": [{"column": "customer_id", "references": "customers.id"}]
       },
       ...
     }
   }
   ```

3. WHEN called, retrieve_schema SHALL connect to the target database, query metadata, and return the dict. It SHALL NOT use embeddings or fuzzy search in this first implementation (see PROJECT_PLAN.md section 4.6 for future semantic search).

4. THE retrieve_schema node SHALL increment `iterations` and return the updated state.

### Requirement 18: MAX_RETRIES Enforced at 3

**User Story:** As a developer, I want retry attempts bounded to prevent infinite loops, so agents cannot retry endlessly.

#### Acceptance Criteria

1. THE constant `MAX_RETRIES` SHALL be defined as 3 in `app/agent/graph.py`.

2. THE router that decides whether to route to fix_sql SHALL check `state["retries"] < MAX_RETRIES`.

3. IF `state["retries"] >= 3`, the router SHALL short-circuit and route directly to final_answer WITHOUT invoking fix_sql. The fix_sql node SHALL never be called once the retry threshold is reached.

4. EVERY fix_sql invocation SHALL increment `state["retries"]` before returning.

### Requirement 19: All 8 Nodes Handle Errors Gracefully

**User Story:** As a developer, I want every node to catch exceptions and update state appropriately, so one node's failure doesn't crash the agent.

#### Acceptance Criteria

1. WHERE a node encounters an exception (network error, database error, etc.):
   - Deterministic nodes SHALL log the error, set `state["error"]` to a user-safe error message, and return the state
   - LLM nodes SHALL log the error, set `state["error"]` and `state["status"]` if appropriate, and return the state

2. NO node SHALL raise an unhandled exception; all exceptions SHALL be caught and converted to state updates.

3. THE error message SHALL never contain database connection strings, API keys, or other secrets.

### Requirement 20: Test Coverage Includes Six Scenarios

**User Story:** As a developer, I want comprehensive test scenarios to catch regressions, so I can confidently change the agent.

#### Acceptance Criteria

1. WHEN `pytest tests/agent/test_graph.py` is run, IT SHALL pass at least these 6 test scenarios:
   - **Happy path**: planner → retrieve_schema → generate_sql → validate_sql → execute_sql → analyze_result → final_answer with `status: "answered"`
   - **Invalid SQL then fix**: generate_sql produces invalid SQL, validate_sql rejects it, fix_sql corrects it, validate_sql accepts it, execute_sql runs it → final_answer with `status: "answered"`
   - **Destructive SQL rejected**: validate_sql detects INSERT/UPDATE/DELETE/DROP and returns `destructive: True`, agent routes to final_answer with `status: "rejected"` and appropriate answer
   - **Retries exhausted**: generate_sql produces SQL, validate_sql fails 3 times (hitting MAX_RETRIES), agent routes to final_answer with `status: "failed"`
   - **Ambiguous question**: planner sets `ambiguity_flag: true`, agent routes to final_answer with `status: "needs_clarification"` and the clarifying question
   - **Iteration budget exceeded**: planner → retrieve_schema → generate_sql → validate_sql → execute_sql → fix_sql (2x due to error) → final_answer: after 10 nodes, agent halts and returns `status: "failed"` with iteration budget error

2. ALL tests SHALL use mocked LLM responses (not real API calls) to ensure determinism and speed.

3. ALL tests SHALL use fixtures for database setup and teardown.
